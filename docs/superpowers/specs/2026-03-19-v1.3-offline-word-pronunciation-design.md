# 文文Lex v1.3 离线单词真实发音设计文档

## 1. 背景

文文Lex `1.2` 已经完成了发音模块第一版：

- 单词详情页和学习页接入了英式 / 美式播放入口
- 发音设置页可管理来源策略、缓存和语音包
- 已有词典音频缓存、在线词典抓取、桥接语音包下载与安装链路
- 系统 `TextToSpeech` 仍是离线兜底能力

但 `1.2` 的“离线语音包”本质仍是 `system_tts_bridge`，不是一个真正可脱离系统朗读质量波动、可覆盖导入词书单词的本地真实发音方案。

用户对 `1.3` 已明确给出以下约束：

- 主目标：优先完成“单词级真实离线发音”
- 口音策略：英式 / 美式分开下载独立语音包
- 覆盖范围：覆盖 App 内所有单词，包括 Excel 导入词书
- 技术路线：本地专用英语发音引擎为主，另外保留联网批量预生成缓存增强
- 包体接受度：单个口音包接受 `500MB+`

因此，`1.3` 的核心不是继续优化桥接包，而是把“离线语音包”升级成真正的本地神经发音包。

## 2. 版本目标

### 2.1 目标

- 在 Android 端接入真正的本地英语神经发音引擎
- 将英式 / 美式拆成两个独立可下载离线包
- 让 App 内任意单词都能走本地真实离线发音，包括导入词书单词
- 首次本地生成后缓存音频，减少重复合成耗时
- 在现有发音调度器中正式加入“原生离线发音”层
- 为后续联网批量预生成缓存保留增强接口
- 明确 runtime、模型、词典/G2P 资源的许可证边界

### 2.2 非目标

- `1.3` 不把主目标扩展到长文本 / AI 整段离线朗读
- 不把大模型直接打进主 APK
- 不引入云端账号或自建服务器
- 不在首版做多说话人切换、情感风格切换或跟读评分
- 不在首版做共享底模去重优化

## 3. 设计原则

- **离线为真，不是桥接伪装**：离线单词发音必须由本地专用引擎生成，而不是继续依赖系统 TTS
- **覆盖导入词书**：不能只覆盖内置词库，要覆盖用户导入的有效单词
- **口音分包**：英式 / 美式各自独立下载、安装、激活和删除
- **主包轻量**：主 APK 只带运行时桥和管理逻辑，大模型外置
- **缓存优先复用**：本地生成过的单词音频必须可直接复用
- **显式许可证管理**：模型、runtime 和字典/G2P 依赖都必须在集成前过一轮许可证审查

## 4. 方案结论

`1.3` 采用以下总路线：

- 运行时：`sherpa-onnx` Android TTS runtime
- 模型方向：优先评估 `Kokoro` 英语模型族
- 用户可见形态：英式包、美式包各自独立下载
- 生成方式：本地实时合成单词音频，首次生成后缓存到本地
- 增强路线：后续可选接入“联网批量预生成并缓存”

### 4.1 选择理由

- `sherpa-onnx` 官方已有 Android TTS 路线与预编译库说明，工程落地风险可控
- `Kokoro` 模型体积和能力更接近当前用户接受的 `500MB+` 区间
- 该路线允许文文Lex 保持单 App 体验，不需要拆成伴生 TTS App
- 与 `1.2` 已有的语音包、下载、安装、激活、缓存框架兼容性最好

### 4.2 放弃的路线

- 不采用“伴生 TTS 引擎 App”方案，因为体验割裂
- 不采用“只做高频词预制音频包”方案，因为无法覆盖导入词书
- 不采用“先联网生成再离线播放”作为主线，因为不满足首发“真实离线”目标

## 5. 总体架构

`1.3` 将离线单词发音定义为一个新层级，而不是替换 `1.2` 全部发音链路。

### 5.1 新主播放链

单词发音优先级升级为：

`本地单词音频缓存 > 本地原生离线发音引擎实时生成 > 在线预生成缓存（增强项） > 1.2 既有兜底链`

其中：

- “本地单词音频缓存”包括历史已生成的离线单词音频
- “本地原生离线发音引擎实时生成”是 `1.3` 主能力
- “在线预生成缓存”不是主线，只是后续增强
- “1.2 既有兜底链”仍保留，用于无包、包损坏、词形异常或 runtime 不可用时兜底

### 5.2 保留的 1.2 组件

以下模块继续沿用，但职责会升级：

- `VoicePackRepository`
- `PronunciationOrchestrator`
- `WordAudioRepository`
- `PronunciationSettingsScreen`
- `VoicePackDownloadWorker`

### 5.3 新增核心模块

- `NativeOfflineWordTtsEngine`
  - 封装 `sherpa-onnx` Android runtime
  - 加载语音包目录中的模型和配置
  - 提供“根据单词生成音频文件”的能力

- `WordPronunciationNormalizer`
  - 对词形做规范化，例如大小写、连字符、撇号、复数/时态的标准输入整理
  - 负责把 UI 词条转成引擎更稳定的输入

- `LicenseManifestVerifier`
  - 检查包内是否带有约定的许可证清单和来源说明
  - 避免运行时下载来历不明的模型包

## 6. 数据模型设计

`1.3` 不再升级主数据库大版本，优先复用 `v3` 的 `voice_packs` 和 `word_audio_assets`，通过增量字段与 manifest 扩展支持真正的原生离线包。

### 6.1 voice_packs 扩展字段

在 `voice_packs` 现有字段基础上，新增或扩展：

- `engineFamily`
  - 示例：`native_neural_tts`
- `modelFamily`
  - 示例：`kokoro`
- `speakerId`
  - 模型内部说话人标识
- `packScope`
  - 首版固定：`word_only`
- `packageFormatVersion`
  - 用于未来兼容升级
- `modelChecksum`
  - 核心模型文件校验值
- `supportsImportedWords`
  - 首版必须为 `true`
- `estimatedStorageBytes`
- `estimatedRamMb`

### 6.2 word_audio_assets 扩展来源类型

在现有来源类型基础上新增：

- `offline_native_cache`
- `offline_native_generated`
- `online_prebuilt_cache`

用途：

- 区分“命中已有本地缓存”与“刚刚由本地引擎生成”
- 为后续排查播放质量和缓存命中率提供依据

### 6.3 设置项

在现有 DataStore 上补充：

- `preferredOfflineVoicePackUk`
- `preferredOfflineVoicePackUs`
- `enableNativeOfflineWordPronunciation`
- `allowOnlinePrebuildCache`
- `nativeWordCacheLimitMb`
- `warmupOnBookSwitch`

## 7. 语音包格式设计

### 7.1 分包策略

每个口音一个独立包：

- `en-gb-offline-word-v1`
- `en-us-offline-word-v1`

首版接受双包各自重复携带部分模型资源，以换取实现简单和运行时稳定。

### 7.2 包内结构

建议目录结构：

```text
<pack-id>/
  manifest.json
  config.json
  model.onnx
  tokens.txt
  lexicon.txt
  speakers.bin
  LICENSES/
    runtime.txt
    model.txt
    lexicon.txt
```

### 7.3 manifest.json 必填项

- `id`
- `name`
- `locale`
- `accent`
- `engineFamily`
- `modelFamily`
- `modelVersion`
- `speakerId`
- `packageFormatVersion`
- `entryFiles`
- `sha256`
- `estimatedStorageBytes`
- `estimatedRamMb`
- `supportsImportedWords`
- `licenses`

## 8. 本地目录规划

- 语音包安装目录：
  - `files/voice-packs/native/<packId>/`
- 本地生成缓存目录：
  - `files/audio-cache/generated/<accent>/<normalizedWord>.wav`
- 在线预生成缓存目录：
  - 首版仍写入同一 generated cache 体系，通过元数据区分来源

## 9. 单词生成与缓存流程

### 9.1 首次播放

1. 页面请求播放单词
2. `PronunciationOrchestrator` 先查本地缓存
3. 未命中时，检查目标口音原生离线包是否可用
4. 进入 `WordPronunciationNormalizer`
5. `NativeOfflineWordTtsEngine` 合成单词音频
6. 写入 `word_audio_assets`
7. 立即播放生成结果

### 9.2 后续播放

1. 查到 `offline_native_cache` / `offline_native_generated`
2. 直接播放，不再重复合成

### 9.3 导入词书支持

只要词条最终能被规范化为有效英文单词或可发音词串，就允许本地生成。

首版不承诺以下异常输入都有高质量效果：

- 混合中英文的脏字段
- 带释义拼接的整句
- 含多个单词、斜杠、括号的复杂原始单元格文本

这些异常值仍回落到 `1.2` 既有兜底链。

## 10. 在线预生成缓存增强

`C3` 作为增强路线，保留但不阻塞 `1.3.0` 首发。

### 10.1 用途

- 对当前词书进行批量预热
- 对高频播放单词做更高质量缓存
- 在用户网络可用时预生成，离线时直接播放

### 10.2 位置

它不是另一套主发音系统，而是 `PronunciationOrchestrator` 里的一个增强来源。

### 10.3 约束

- 不能依赖云端服务作为主链路
- 不能要求用户登录
- 生成结果必须回写本地缓存和元数据

## 11. 许可证与合规边界

这部分必须前置，不允许等代码写完再补。

### 11.1 必做项

- 建立 `runtime + model + lexicon/G2P` 的 BOM 清单
- 为每个候选组件记录：
  - 来源仓库
  - 许可证
  - 是否允许随 App 分发
  - 是否要求附带版权声明
  - 是否存在 copyleft 风险

### 11.2 集成门槛

如果某候选链条必须绑定不可接受的 GPL / copyleft 组件，则不能直接进入文文Lex 正式主线。

### 11.3 当前工程判断

从现有公开资料看：

- `sherpa-onnx` runtime 本身可作为主线候选
- `Kokoro` 模型方向值得优先评估
- `eSpeak NG` 相关依赖需要重点核查，不能默认安全

本设计文档不是法律意见，但要求工程上先做许可证审查，再做正式集成。

## 12. UI 与用户体验变化

### 12.1 发音设置页

新增：

- 原生离线发音开关
- 英式包 / 美式包安装状态
- 预计存储占用和 RAM 提示
- 当前包版本与来源展示
- “为当前词书预热离线发音缓存”入口（增强项可先灰掉）

### 12.2 单词详情页

新增状态提示：

- 当前播放来源是否为“原生离线发音”
- 是否已命中本地缓存
- 是否刚刚完成本地生成

### 12.3 学习页

继续只暴露“播放”交互，不把复杂技术细节堆给用户。

## 13. 风险与回退策略

### 13.1 主要风险

- Android NDK / JNI 集成复杂度高
- 语音包体积大，下载失败率和存储占用会明显上升
- 不同设备上的内存占用差异可能导致低端机不稳定
- 模型、词典、G2P 许可证边界可能卡住

### 13.2 回退策略

- 若原生离线包不可用，继续保留 `1.2` 词典音频和系统 TTS 兜底
- 若单词无法被规范化，回退到现有链路
- 若低内存设备无法稳定运行，可在设置页提示关闭原生离线能力

## 14. 版本切分

### 14.1 v1.3.0

- 接入原生离线单词发音 runtime
- 英式 / 美式分包下载、校验、安装、激活
- 单词详情页和学习页支持本地原生离线发音
- 支持导入词书单词
- 首次生成后本地缓存复用
- 完成许可证 BOM 和语音包清单约束

### 14.2 v1.3.x

- 联网批量预生成缓存
- 为当前词书一键预热高频音频
- 双包共享底模，降低重复占用
- 再评估向例句和 AI 长文本朗读扩展

## 15. 验收标准

`1.3` 首发被视为达标，至少满足：

- 已安装英式或美式原生离线包后，App 内任意有效英文单词都可离线播放
- 导入词书中的英文单词可以走本地发音链路
- 第二次播放同一单词时能命中本地缓存
- 无离线包、包损坏或异常词条时不会让播放链路整体失效
- Release 文档中明确写清语音包大小、来源、限制和许可证说明
