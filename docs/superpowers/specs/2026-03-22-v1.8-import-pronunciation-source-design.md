# 文文Lex v1.8 导入闭环与统一发音源中心设计文档

## 1. 背景

文文Lex 在 `v1.7` 已经把动态复习、目标系统、升级安全、诊断中心和发版护栏补齐，产品与工程底座已经明显更稳。但当前还有两类高频问题已经影响到下一轮体验升级：

- Excel 导入虽然已经支持 `.xlsx`、本地预览和 AI 适配，但“结构诊断不够明确、修复路径不够清晰、导入后补全过程偏散”仍然存在
- 发音链路虽然已经跑通词典音频、本地 native 语音包和系统 TTS 兜底，但“离线语音包、本地模型、云端 TTS、预生成缓存、默认源、快速切换、后台生成”目前还是碎片化状态

同时，真机上已经出现新的发音包安装问题。当前实现里，下载阶段会把整个归档一次性读进内存，payload 校验阶段也会整文件 `readBytes()`，这会放大大包安装时的 OOM 风险，难以支撑更大的本地引擎包和后续多来源语音资产。

用户本轮已经明确提出：

- `1.8` 主线选 `A3`：以“导入闭环增强”为主，同时做词库质量第一批补强
- 发音系统不再只围绕“离线语音包”补丁式扩展，而是改成统一的“发音源中心”
- 本地模型不应默认实时边生成边播放，而要优先支持预生成语音资产，避免卡顿、发热和播放延迟
- 云端 TTS 不只用于在线朗读，还应能生成离线缓存；多个 TTS 模型或多个来源生成的语音资产要能共存、快速切换、设置默认值
- 小米 MiMo TTS 要作为正式 provider 接入，并支持官方内置 voice 与 style 预设切换，同时保留高级模式
- 还要补上 API 检测按钮、断点续传、后台生成和离线缓存管理界面

因此，`v1.8` 的目标不是再堆几个孤立入口，而是把“导入闭环 + 发音源中心 + 生成与缓存基础设施”收成一套统一、可扩展、可发版的正式能力。

## 2. 版本目标

### 2.1 目标

- 把 Excel 导入升级成“诊断 -> 修复 -> 预览 -> 导入 -> 后续补全”的完整闭环
- 落地“轻微问题自动修、严重问题先提示再决定是否调 AI”的导入分级策略
- 对内置词库和导入词书补第一批质量增强入口，至少覆盖音标、近义词、反义词、易混词、例句和词形变化
- 把本地引擎包、词典音频、云端 TTS、预生成离线音频资产统一抽象成发音源
- 支持发音源默认值、快速切换、源级缓存共存、源级后台生成和离线缓存管理
- 支持本地模型与云端 TTS 两条链都能预生成离线语音资产
- 接入通用云 TTS provider 框架，并正式接入 Xiaomi MiMo TTS 作为首个 provider
- 增加 API 检测按钮，能验证 key、模型和最小 TTS 请求是否可用
- 修复当前本地语音包下载/安装链路的内存风险，补齐断点续传与低内存安装能力
- 保持本地优先、无账号、无自建服务器、GitHub 云端发版的边界不变

### 2.2 非目标

- `v1.8` 不引入云端账号、自建服务器、多端同步
- 不把导入增强扩展成复杂的在线表格编辑器
- 不在本轮做整库一次性全量高质量语义补全，首版只做第一批补强入口和批处理管线
- 不把本地模型默认改成实时单词发音主链
- 不在 `v1.8` 接入完整的语音克隆能力
- 不做应用内热更新或静默更新 APK
- 不重写学习流、目标系统和 AI 计划中心主结构

### 2.3 发版分层

为避免 `v1.8` 范围失控，本轮明确拆成 `P0 必发` 和 `P1 可滑出` 两层：

#### P0 必发

- 导入页完成 `B3` 分级诊断与修复闭环
- 导入后补全入口和内置词书补全入口都打通
- 统一发音源中心第一版可用
- 本地引擎源、词典源、MiMo 云 TTS 源都能进入同一套发音源列表
- 支持默认发音源、快速切换
- 支持单个单词、指定词书、分批、后台生成
- 缓存管理至少具备查看与清理入口
- 本地模型与 MiMo TTS 都能生成离线语音资产
- 语音包下载支持断点续传、低内存校验与安装
- MiMo provider 与 API 检测按钮可用
- Room `7 -> 8` 与备份 `v6 -> v7` 完成

#### P1 可滑出

- 缓存管理页里的细粒度统计，如命中率趋势、失败趋势、按任务维度的长期分析
- 内置词书第一批质量补强的默认批量策略优化
- MiMo 高级 style 的更多模板预置与高级提示文案
- 更完整的任务历史页和更细的后台调度策略可视化

如果 `P1` 发生滑出，不影响 `v1.8` 可发版定义；滑出的项顺延到下一轮版本。

## 3. 已确认的产品约束

用户已经确认以下决策，这些决策直接锁定 `v1.8` 的边界：

- 主线是 `A3`：
  - 导入闭环增强优先
  - 词库质量做第一批补强
- 导入异常处理采用 `B3`：
  - 轻微问题自动修
  - 严重问题先提示，再让用户决定是否调用 AI
- 发音系统采用 `B`：
  - 统一发音源中心，而不是继续在旧“离线语音包”页上叠补丁
- 本地模型播放策略采用 `G1`：
  - 默认不走实时单词合成主链
  - 优先播放预生成缓存
  - 缓存没命中时回退词典音频或云端 TTS
- 生成任务采用 `H1`：
  - 按发音源组织，不按词书做顶层分组
- MiMo 预设策略采用 `I3`：
  - 默认开放安全预设
  - 高级模式开放自定义 style
- 语音资产要求：
  - 本地模型也要支持预生成
  - 云端 TTS 生成结果要能落地成离线缓存
  - 多个发音源、多种预设生成的离线语音资产必须共存
  - 支持快速切换当前发音源和设置默认值
- 生成入口要求：
  - 支持单个单词生成
  - 支持指定词书生成
  - 支持分批生成
  - 支持后台生成

这些约束意味着，`v1.8` 不能再沿用“一个页面管所有发音逻辑、一个缓存池装所有结果”的做法，而必须把来源、资产、任务、默认值和页面入口统一建模。

## 4. 方案结论

`v1.8` 采用“三层统一”方案：

- 产品层：
  - 导入闭环中心
  - 发音与语音资产中心
- 领域层：
  - 发音源 `PronunciationSource`
  - 引擎型语音包 `VoicePack`
  - 预生成离线语音资产 `GeneratedAudioAsset`
- 基础设施层：
  - 导入诊断与修复管线
  - 语音生成任务管线
  - 低内存下载 / 校验 / 安装管线

核心结论如下：

- 不把本地引擎包和预生成音频资产混成同一个底层对象
- 但在 UI 层统一为“发音源中心”，用户不需要理解内部实现差异
- 本地模型与云端 TTS 都可以生成离线语音资产
- 播放逻辑优先使用离线缓存命中，不把实时推理当默认体验
- MiMo TTS 不做特例硬编码，而是作为通用云 TTS provider 的首个实现

## 5. 总体架构

### 5.1 组件职责

- `ImportDiagnosisEngine`
  - 读取工作表结构
  - 输出“字段识别结果 + 问题严重度 + 可自动修复项 + 可 AI 修复项”

- `ImportRepairCoordinator`
  - 负责先执行本地自动修复
  - 对剩余高风险问题触发 AI 适配
  - 输出最终可导入预览

- `ImportEnrichmentCoordinator`
  - 在导入完成后，负责批量补音标和第一批质量补强任务入口
  - 首版不强制自动跑，先提供明确入口和任务状态

- `PronunciationSourceRegistry`
  - 统一管理所有发音源
  - 负责列出、启用、禁用、切换默认值

- `VoicePackInstallerV2`
  - 负责引擎型本地语音包下载、校验、解压和安装
  - 支持断点续传、低内存校验和原子替换

- `CloudTtsProvider`
  - 通用云 TTS provider 接口
  - 首版实现 `MiMoTtsProvider`

- `AudioGenerationCoordinator`
  - 接收“按发音源生成”的任务
  - 调度单词、词书、分批和后台生成

- `GeneratedAudioAssetRepository`
  - 管理离线语音资产索引
  - 负责缓存命中、清理、统计和共存规则

- `SourcePlaybackResolver`
  - 在播放时根据当前发音源、场景和缓存状态解析最终播放路径

- `ApiHealthChecker`
  - 为云 TTS 档案提供最小可用性检测
  - 输出结构化检测结果

### 5.2 架构原则

- 统一抽象，避免页面层直接判断“这是语音包还是缓存”
- 实时播放链优先稳定，不优先炫技
- 生成链和播放链分离，避免一边合成一边播导致卡顿
- 云 TTS 与本地模型遵循同一套任务 / 缓存 / 默认值规则
- 错误信息先结构化，再投影到 UI 文案
- 导入与补全任务尽量复用现有 AI 档案与 WorkManager 基础设施

## 6. 数据模型设计

### 6.1 现有模型保留

以下现有模型继续保留，但职责需要收紧：

- `VoicePackEntity`
  - 继续表示“引擎型语音包”或“安装型运行时资源”
  - 不再承载所有发音来源概念

- `WordAudioAsset`
  - 继续表示单条已缓存的音频资产
  - 但需要扩展源级命名空间和任务来源信息

### 6.2 新增核心模型

建议新增以下结构：

- `PronunciationSourceEntity`
  - 顶层发音源
  - 字段建议：
    - `id`
    - `name`
    - `sourceType`：`dictionary` / `local_native` / `cloud_tts`
    - `accent`
    - `enabled`
    - `isDefaultForWord`
    - `isDefaultForLongText`
    - `providerProfileId`
    - `backingVoicePackId`
    - `sortOrder`
    - `createdAt`
    - `updatedAt`

- `PronunciationSourcePresetEntity`
  - 某个发音源下的可切换预设
  - 例如 MiMo 的 `default_en`、`mimo_default`
  - 字段建议：
    - `sourceId`
    - `presetId`
    - `displayName`
    - `voice`
    - `styleTemplate`
    - `advancedStyleEnabled`
    - `isDefaultPreset`

- `GeneratedAudioAssetEntity`
  - 预生成或在线生成后落盘的离线语音资产索引
  - 字段建议：
    - `id`
    - `sourceId`
    - `presetId`
    - `accent`
    - `sceneType`：`word` / `example_sentence` / `ai_explanation`
    - `wordId`
    - `contentHash`
    - `textPreview`
    - `localPath`
    - `sizeBytes`
    - `generatedAt`
    - `generationMethod`：`local_native_batch` / `cloud_tts_online` / `dictionary_fetch`
    - `taskId`
    - `namespace`
    - `assetState`：`ready` / `stale` / `missing`

- `AudioGenerationTaskEntity`
  - 一次生成任务
  - 字段建议：
    - `id`
    - `sourceId`
    - `presetId`
    - `scopeType`：`single_word` / `book` / `batch`
    - `scopeRef`
    - `status`
    - `totalItems`
    - `completedItems`
    - `failedItems`
    - `createdAt`
    - `updatedAt`
    - `runInBackground`

- `AudioGenerationTaskItemEntity`
  - 任务中的单个处理单元
  - 字段建议：
    - `taskId`
    - `itemKey`
    - `wordId`
    - `text`
    - `status`
    - `failureReason`
    - `attemptCount`
    - `generatedAssetId`

- `ImportDiagnosisSnapshot`
  - 导入诊断与修复摘要
  - 可独立表，也可扩展现有 `ImportBatch`
  - 至少记录：
    - 字段识别置信结果
    - 自动修复数量
    - AI 修复数量
    - 高风险问题数量
    - 最终导入条目数

### 6.3 共存规则

同一个单词允许被多个发音源、多种预设分别生成并共存。例如：

- 本地 US 引擎源生成一份
- 本地 UK 引擎源生成一份
- MiMo `default_en + calm` 生成一份
- MiMo `mimo_default + happy` 再生成一份

因此，缓存命名空间不能只用 `word + accent`，至少应包含：

- `sourceId`
- `presetId`
- `sceneType`
- `contentHash`
- `accent`

### 6.4 数据库与备份升级

本轮建议同步升级：

- Room：`7 -> 8`
- 备份：`v6 -> v7`

`v7` 备份至少要覆盖：

- 发音源配置
- 发音源默认值
- 发音源预设选择
- 语音生成任务索引
- 离线语音资产索引摘要
- 导入诊断摘要

仍保持以下规则不变：

- API Key 不进入备份文件
- 仅保留档案元信息、路由与 provider 配置

离线语音资产的备份语义首版明确如下：

- 不备份音频文件本体
- 不保证跨设备恢复后原有 `localPath` 继续有效
- 只备份“发音源配置 + 任务索引 + 资产摘要”
- 恢复后，所有找不到本地文件的资产索引统一标记为 `stale`
- `stale` 资产不会参与命中，用户可在缓存管理页中清理或重新生成

这样可以避免：

- 备份文件体积随音频资产暴涨
- 跨设备恢复后路径失效造成大量脏数据
- 本地绝对路径进入备份后产生不可控兼容问题

`stale` 是持久化状态，不是运行时临时计算值。恢复流程中如果发现：

- 资产文件不存在
- 路径不可访问
- 路径来自其他设备或旧安装目录

则直接把对应资产落库为 `assetState = stale`，后续：

- 不参与缓存命中
- 不参与“可直接播放资产数”统计
- 但仍保留在缓存管理页里，供用户清理或重新生成

## 7. 导入闭环设计

### 7.1 分级诊断策略

导入诊断首版按两级处理：

- `轻微问题`
  - 可直接本地自动修
  - 例如：
    - 中英文逗号混用
    - 空白行、标题行、注释行
    - 单元格前后空格
    - 大小写不规范
    - A/B 列高置信结构识别

- `严重问题`
  - 先明确提示，再由用户决定是否调用 AI
  - 例如：
    - 列位不明确
    - 多工作表冲突
    - 合并单元格导致结构断裂
    - 单词列 / 释义列大面积缺失
    - 含大量非词条内容

### 7.2 导入页面流程

导入页升级为以下流程：

1. 选择 Excel 文件
2. 本地解析并生成首轮预览
3. 展示诊断摘要
4. 自动执行轻微问题修复
5. 对严重问题提供“AI 修复”按钮
6. 展示修复后预览
7. 确认导入
8. 提示后续补全入口

### 7.3 第一批质量补强

本轮只补第一批，不追求一次做满。补强范围：

- 英式 / 美式音标
- 近义词
- 反义词
- 易混词
- 例句
- 词形变化

首版采用“可批处理、可中断、可回看结果”的任务模式，而不在导入完成后强制全部自动跑完。

第一批补强入口明确放在两个位置：

- 导入完成后的“继续补全”入口
- 词书详情页中的“质量补强”入口

其中词书详情页同时覆盖：

- 导入词书
- 内置词书

这样 `v1.8` 的质量补强不会只服务导入链路，也能直接作用于现有内置词书。

## 8. 统一发音源中心设计

### 8.1 发音源分类

首版支持以下发音源：

- `词典音频源`
  - 在线抓取和本地词典缓存

- `本地引擎源`
  - 基于现有 native voice pack
  - 英式 / 美式可分别作为不同源存在

- `云 TTS 源`
  - 首版先接 MiMo
  - 后续其他 provider 可接入同一框架

### 8.2 默认值与快速切换

默认值拆成两层：

- `单词发音默认源`
- `长文本朗读默认源`

快速切换至少要覆盖：

- 单词详情页
- 学习页

切换规则：

- 临时切换不强制写回全局默认
- 最近一次成功切换可记忆为会话级偏好
- 全局默认仍由发音中心统一维护

### 8.3 播放解析顺序

按用户确认的 `G1`，默认解析顺序如下：

#### 单词发音

1. 当前发音源下的离线预生成缓存
2. 若当前源为词典源，则尝试词典音频 / 词典缓存
3. 若当前源为云 TTS，则在线请求并落缓存
4. 若当前源为本地引擎源，默认不实时推理，改回退词典或云 TTS
5. 系统 TTS 兜底

#### 例句 / 长文本 / AI 讲解

1. 当前发音源下的离线预生成缓存
2. 若当前源为云 TTS，则在线请求并落缓存
3. 若设置允许，再尝试系统 TTS

### 8.4 语音资产共存

不同发音源、不同预设生成的离线语音资产必须并存，不能互相覆盖。缓存管理页面应支持：

- 只删某个发音源的缓存
- 只删某本词书在某个发音源下的缓存
- 只删某次批处理任务生成的缓存
- 只删单条资产

### 8.5 fallback 归属规则

播放 fallback 的归属首版明确如下：

- 用户当前选中的发音源，表示“首选来源”
- 真正成功返回音频的来源，表示“实际来源”

当发生 fallback 时：

- 播放状态提示显示实际来源
- 新生成或新抓取的离线语音资产归属到实际来源，而不是首选来源
- 缓存命中率、缓存占用、清理入口都按实际来源统计
- 首选来源侧仅记录一次“fallback 事件”，用于后续问题定位和体验统计

系统 TTS 属于特殊兜底，不作为正式 `PronunciationSource`：

- 不进入发音源中心列表
- 不生成离线语音资产
- 不参与源级缓存占用统计
- 只在播放态中显示“系统朗读兜底”
- 只记录一次 fallback 事件，用于诊断和体验统计

例如：

- 当前首选为“本地 US 引擎源”
- 该源缓存 miss，且按 `G1` 不做实时推理
- 最终由 MiMo TTS 成功生成并播放

则本次结果应：

- 在 UI 上显示“实际来源：MiMo TTS”
- 资产落到 MiMo 源的缓存命名空间
- MiMo 的缓存统计增加
- 本地 US 源只记录一次 fallback 事件，不视为缓存命中

## 9. 本地模型与云 TTS 的预生成设计

### 9.1 统一生成入口

每个发音源都支持：

- 单个单词生成
- 指定词书生成
- 分批生成
- 后台生成

任务按发音源组织，而不是按词书做顶层分组。

### 9.2 本地模型生成

本地引擎源在 `v1.8` 的主能力不是实时生成，而是：

- 作为“能生产语音资产”的发音源
- 在后台批量生成离线音频
- 让用户后续直接播放缓存结果

这样可以规避：

- 首次合成等待过长
- 播放卡顿
- 发热
- 前台切换时中断

### 9.3 云 TTS 生成

云 TTS 不只负责在线朗读，也要支持：

- 生成单词离线缓存
- 生成例句离线缓存
- 生成 AI 讲解离线缓存

即，云 TTS 生成结果也应纳入统一的离线语音资产体系。

## 10. Xiaomi MiMo TTS 接入设计

### 10.1 官方事实

MiMo 平台官方文档明确提供：

- OpenAI 兼容接口
- TTS 模型 `mimo-v2-tts`
- 请求地址 `https://api.xiaomimimo.com/v1/chat/completions`
- `api-key` 或 `Authorization: Bearer` 两种鉴权
- 音色参数 `audio.voice`
- 语音格式参数 `audio.format`

参考：

- [Speech Synthesis](https://platform.xiaomimimo.com/docs/usage-guide/speech-synthesis.md)
- [OpenAI API Compatibility](https://platform.xiaomimimo.com/docs/api/chat/openai-api.md)
- [MiMo-V2-TTS Release](https://platform.xiaomimimo.com/docs/news/v2-tts-release.md)

### 10.2 首版 provider 设计

新增 `MiMoTtsProvider`，通过通用 `CloudTtsProvider` 接口接入。

首版支持：

- 模型固定为 `mimo-v2-tts`
- 内置 voice：
  - `mimo_default`
  - `default_zh`
  - `default_en`
- style 预设模板
- 高级模式自定义 style
- 非流式请求生成 `wav`
- 可选流式方案作为后续增强

### 10.3 预设能力开放策略

按 `I3` 落地：

- 默认模式：
  - 只开放安全预设
  - 例如音色、平静、开心、讲解、低声等模板

- 高级模式：
  - 允许用户自定义 style 文本
  - 但首版仍需加说明，避免写错 style 造成不可预测输出

### 10.4 API 检测按钮

每条云 TTS 档案增加“检测 API”按钮，最小检测项包括：

- 是否能成功鉴权
- 模型是否可用
- 最小 TTS 请求是否成功返回
- 返回音频能否被解码
- 记录一次基础响应时延

检测结果要结构化返回，而不是只弹一句“成功 / 失败”。

## 11. 语音包下载、续传与低内存安装设计

### 11.1 当前问题

当前实现存在两个关键风险：

- 下载时整包 `readBytes()` 进内存
- payload 校验时整文件 `readBytes()` 进内存

这会让大包在真机上更容易触发 OOM。

### 11.2 修复策略

`VoicePackInstallerV2` 首版应具备：

- 流式下载到 `.part` 文件
- `HTTP Range` 断点续传
- 若服务端不支持 Range，则自动回退为整包重下
- 下载元信息 `.meta` 记录
- 流式 checksum 计算
- 流式解压
- 安装到临时目录，校验通过后原子替换正式目录

### 11.3 错误分类

错误至少拆成：

- 下载失败
- 网络中断
- 校验失败
- 存储空间不足
- 内存不足
- 安装失败
- 运行时不兼容

UI 不再只显示“安装失败”，而要展示更接近真实根因的文案。

## 14. 风险与取舍

### 14.1 主要风险

- 发音源抽象如果做得过重，会拖慢 `1.8` 实现进度
- MiMo TTS 虽然是 OpenAI 兼容接口，但 TTS 返回与当前通用文本模型调用仍有差异，provider 层必须隔离
- 批量生成如果不控制节奏，可能带来电量、流量和空间占用问题
- 导入补全过程如果首版范围过大，容易稀释主线

### 14.2 取舍原则

- 优先让结构正确，再扩展 provider 数量
- 优先让缓存、默认值和任务管理稳定，再谈复杂实时推理
- 词库质量首版只做第一批补强入口，不追求把所有维度一次做满
- `v1.8` 先以 MiMo 为首个正式云 TTS provider，不在同一版同时接多家

## 15. 结论

`v1.8` 的核心不是“再加一个 TTS 按钮”或“再补几个导入文案”，而是把文文Lex 从“能导入、能发音、能装本地包”推进到：

- 导入更稳、更清楚、更容易修
- 发音来源统一、可切换、可设默认
- 本地模型和云 TTS 都能沉淀成离线可复用资产
- 大包下载和安装更可靠
- 后续新增其他 TTS provider 时，不需要再重做一套页面和缓存逻辑

这版完成后，文文Lex 的发音系统会第一次真正从“功能堆叠”升级到“来源统一、任务统一、资产统一”的可扩展底座。
