# 文文Lex v1.7 学习效果增强与交付护栏设计文档

## 1. 背景

文文Lex 在 `v1.6` 已经完成了学习统计、长期摘要投喂、AI 计划效果回看和备份 `v5` 的第一版闭环，但当前仍有两个明显缺口：

- App 已经能看到学习数据，但“今天该复习什么”仍主要依赖较轻的调度逻辑，动态性不够
- App 已经有每日目标和统计页，但“阶段目标、周目标、里程碑反馈”还没有形成稳定产品体验
- GitHub 云端发版已经跑通，但升级安全、发版护栏和问题定位能力仍偏人工

结合本轮确认，`v1.7` 不走单一功能扩展路线，而是同时推进两条主线：

- 学习效果主线：让复习顺序和目标推进真正服务记忆效率
- 工程交付主线：让升级、发版、排障更稳，避免后续版本越做越难维护

因此，`v1.7` 的目标不是引入一套过度复杂的新系统，而是在现有 `LearningRecord`、`ReviewScheduler`、`dailyGoal`、`analyticsSnapshot`、GitHub Actions 和本地备份链路上，补出第一版真正可用的“动态复习 + 阶段目标 + 升级/发版/诊断护栏”。

## 2. 版本目标

### 2.1 目标

- 把当前偏静态的复习调度升级为“动态复习引擎 `v1`”
- 为每个单词补充更适合排序和追踪的学习信号
- 新增每日目标、每周目标、连续学习和阶段里程碑的统一目标系统
- 让首页、学习页、统计页都能看到更清晰的目标推进反馈
- 增加升级安全链路，降低 Room 迁移、备份恢复和版本切换的风险
- 增加发版护栏，减少版本号、更新日志、Release 资产和 smoke 回填脱节
- 增加本地诊断能力，方便后续定位“用户这边到底出了什么问题”
- 保持本地优先、无账号、无自建服务器、GitHub 云端发版的既有边界

### 2.2 非目标

- `v1.7` 不引入云端账号、自建服务器或多端同步
- 不做完整自适应教学平台，也不在首版做复杂的个体遗忘曲线拟合
- 不把学习模式扩展成大量新玩法，仍以现有学习流和复习流为主
- 不在 `v1.7` 做应用内自动下载并静默更新 APK
- 不引入外部崩溃平台或在线日志上报服务
- 不重写整套发音链路、词书体系或 AI 计划中心

## 3. 已确认的产品约束

用户已经确认以下约束，这些约束直接决定 `v1.7` 的边界：

- `v1.7` 必须同时覆盖学习效果与工程交付，不只做单侧增强
- 学习侧的优先级是：
  - `复习算法升级`
  - `目标与阶段推进`
- 工程侧的优先级是：
  - `升级安全`
  - `发版护栏`
  - `问题定位`
- 首版要“都覆盖”，但每块先做可用底座，不追求一次做满
- 本轮继续保持“本地优先 + AI API 可选增强 + GitHub 云端 CI/Release”基线
- 由于当前本机仍缺 Java runtime，本轮最终验证仍以 GitHub Actions 为准

这些约束意味着，`v1.7` 不应该做成一个大而散的功能堆，而应该收敛为 6 个能互相配合的能力包：

- 动态复习引擎
- 阶段目标系统
- 学习反馈采集增强
- 升级安全增强
- 发版护栏增强
- 诊断与排障工具

## 4. 方案结论

`v1.7` 采用“双主线、六能力包”路线：

- 学习效果侧：
  - 在现有 `LearningRecord` 和 `ReviewScheduler` 基础上扩展学习信号
  - 引入新的复习优先级计算与今日队列装配
  - 把当前单一 `dailyGoal` 升级为“日/周/阶段”目标体系
- 工程交付侧：
  - 在 App 启动与备份链路中增加升级前快照、迁移校验和恢复兜底
  - 在脚本和 GitHub Actions 中增加发版一致性检查
  - 在 App 内提供诊断中心和导出能力

不采用以下路线：

- 不单独新建第五个主 Tab 承载目标或诊断
- 不把诊断能力依赖到在线后台
- 不把复习算法直接写死成单一 SM-2 克隆，也不首版就开放大量调参入口
- 不在 `v1.7` 内引入复杂的自动更新分发系统

## 5. 总体架构

### 5.1 组件职责

- `ReviewPriorityEngine`
  - 基于遗忘风险、最近错误、反应时、超期程度和熟练度计算复习优先级
  - 输出结构化排序分，不让 UI 自己拼逻辑

- `DailyQueueComposer`
  - 按“救火复习 / 常规复习 / 新词引入”三个层次生成今日队列
  - 负责动态平衡当前目标、待复习积压和新词推进节奏

- `GoalProgressTracker`
  - 维护日目标、周目标、连续天数和阶段里程碑状态
  - 负责把学习结果聚合成首页和“我的”页可展示的目标卡片

- `LearningSignalRecorder`
  - 记录答题正确率、反馈类型、反应时、连续错误、跳过和发音使用等结构化信号
  - 为复习排序、统计页和 AI 长期摘要同时提供输入

- `UpgradeSafetyCoordinator`
  - 在新版本首次启动前后处理升级快照、迁移结果校验和恢复入口暴露

- `DataIntegrityVerifier`
  - 对关键表、关键设置和 AI 摘要字段做迁移后完整性检查
  - 只给出结构化结果，不直接耦合 UI 文案

- `DiagnosticsCenter`
  - 汇总本地关键日志、环境信息、版本信息、迁移结果和最近错误摘要
  - 支持一键导出诊断包

- `ReleaseGuardrails`
  - 由脚本与 GitHub Actions 共同组成
  - 负责版本号、`CHANGELOG.md`、Release 资产、smoke 文档模板的一致性检查

### 5.2 架构原则

- 优先扩展现有模型，不做无关重构
- 调度、目标、诊断都先结构化，再投影到页面
- 学习算法负责“今天学什么”，目标系统负责“做到哪里算完成”
- 升级安全要覆盖“迁移前快照 -> 迁移后校验 -> 失败可恢复”三段
- 发版护栏要尽量前置到 CI，而不是等 Release 完成后再人工发现问题

## 6. 数据模型设计

### 6.1 学习记录扩展

当前 `LearningRecord` / `LearningRecordEntity` 已包含：

- `mastery`
- `familiarityState`
- `nextReviewAt`
- `reviewCount`
- `lapseCount`
- `consecutiveCorrectCount`
- `lastReviewedAt`
- `lastOutcome`
- `confusionWeight`
- `similarSpellingWeight`

`v1.7` 首版建议在现有主表上继续扩字段，而不是另起学习画像表。新增字段建议如下：

- `lastResponseLatencyMs`
  - 最近一次有效反馈的反应时
- `averageResponseLatencyMs`
  - 滚动平均反应时
- `consecutiveMistakeCount`
  - 连续错误次数
- `lastMistakeAt`
  - 最近一次错误时间
- `lastStudiedBookId`
  - 最近一次主要学习来源词书
- `forgettingRiskScore`
  - 遗忘风险分
- `reviewPriorityScore`
  - 当前复习优先级分
- `proficiencyBand`
  - 熟练度分层，如 `new`、`unstable`、`growing`、`solid`

首版继续保持“单词一行主记录”的设计，不额外拆独立画像表，优先降低迁移和备份复杂度。

### 6.2 目标系统建模

当前只有 `SettingsRepository.dailyGoal`。`v1.7` 需升级为“设置 + 进度快照”双层模型：

- 设置层：
  - `dailyGoal`
  - `weeklyGoal`
  - `phaseTargetWords`
  - `phaseName`

- 进度层：
  - `dailyGoalProgress`
  - `weeklyGoalProgress`
  - `currentStreakDays`
  - `bestStreakDays`
  - `phaseCompletedWords`
  - `phaseCompletedAt`

实现上优先使用：

- 简单目标配置继续存 `DataStore`
- 需要回溯的阶段进度和里程碑历史进入 Room

### 6.3 诊断模型

`v1.7` 首版不引入在线崩溃平台，但需要本地结构化诊断数据。建议新增轻量诊断表或本地文件日志，至少覆盖：

- 最近版本号与安装时间
- 最近数据库迁移结果
- 最近备份导入/导出结果
- 最近语音包安装/播放失败摘要
- 最近 AI 调用失败摘要
- 关键页面加载失败摘要

首版可优先采用“结构化本地日志文件 + 少量 Room 快照字段”的混合方式，避免给主数据库塞进高频冗余日志。

### 6.4 迁移与备份

由于本轮会扩展学习记录、目标进度与诊断状态，版本升级应同步推进：

- Room：`6 -> 7`
- 备份：`v5 -> v6`

`v6` 备份至少要覆盖：

- 扩展后的学习记录字段
- 新的目标设置与阶段进度
- 迁移校验摘要
- 诊断中心所需的最小快照信息

同时保持对旧 `v1` 到 `v5` 备份的兼容导入。

## 7. 动态复习引擎设计

### 7.1 排序目标

动态复习引擎首版解决三个问题：

- 哪些词最该优先复习
- 今日目标有限时，新词和复习词怎么分配
- 哪些词需要“救火式回炉”

### 7.2 优先级因子

首版优先级分由以下维度组合：

- `nextReviewAt` 是否已超期，以及超期多久
- 最近是否连续出错
- 最近反应时是否明显偏慢
- 当前 `mastery` 与 `proficiencyBand`
- `confusionWeight` 与 `similarSpellingWeight`
- 最近 24 小时内是否刚复习过

原则如下：

- 已超期 + 连续出错的词优先级最高
- 反应很慢但答对的词，不应和稳定掌握词等价
- 刚学过且状态稳定的词，要适当后置

### 7.3 今日队列装配

今日队列首版建议拆成三段：

- `rescue`
  - 连续错误、刚忘、强混淆、强超期词
- `review`
  - 常规到期或即将到期词
- `new`
  - 今日可引入的新词

分配策略：

- 当积压严重时，优先压缩 `new`
- 当救火词占比过高时，首页要提示“今天先回稳，不再猛推新词”
- 阶段目标仍保留推进新词的能力，但不强压过高风险复习

### 7.4 与现有 AI 能力的关系

`v1.7` 不把复习排序完全交给 AI 决策。首版原则是：

- 调度核心仍由本地规则完成
- AI 可在长期摘要中读取新的学习信号
- AI 主要影响策略解释和节奏建议，不直接替代本地队列装配

## 8. 目标与阶段推进设计

### 8.1 目标层级

`v1.7` 目标系统拆为三层：

- 每日目标
- 每周目标
- 阶段目标

其中：

- 每日目标解决“今天做多少”
- 每周目标解决“这一周有没有稳住节奏”
- 阶段目标解决“这一轮到底在推进什么”

### 8.2 页面投影

- 首页：
  - 继续保留今日目标卡
  - 新增本周进度与阶段说明摘要
- 学习页：
  - 在阶段结束、目标完成、连续打卡中断等节点给出轻提示
- 我的页：
  - 增加目标设置与阶段管理入口
- 统计页：
  - 补充目标完成率、周节奏和阶段推进趋势

### 8.3 阶段里程碑

首版阶段系统不做复杂课程编排，只支持：

- 阶段名称
- 目标词量
- 已完成词量
- 阶段起止时间
- 阶段完成反馈

阶段完成后可给出简单总结文案，并为后续 AI 计划输入提供更稳定的“最近阶段表现”上下文。

## 9. 升级安全与交付护栏设计

### 9.1 升级安全

`v1.7` 升级安全必须覆盖三件事：

- 迁移前尽可能留下可恢复快照
- 迁移后自动做完整性校验
- 一旦异常，用户能看见并进入恢复路径

首版建议：

- 新版本首次启动前，复制旧数据库文件生成一次“升级前快照”
- 数据库打开并迁移完成后，执行关键数据校验：
  - 词书数量
  - 学习记录数量
  - AI 记忆主字段是否可读
  - 目标设置是否完整
- 若校验失败：
  - 在首页或“我的”页暴露高优先级异常卡片
  - 提供恢复备份、导出诊断包、查看错误摘要入口

### 9.2 发版护栏

`v1.7` 发版护栏主要落在云端脚本和文档流程：

- 校验版本号是否符合 `major.minor`
- 校验 `CHANGELOG.md` 是否存在对应版本小节
- 校验 `README.md` / `development-progress.md` / `collaboration-handbook.md` 是否已同步
- 校验 Release 资产命名与 checksum 文件完整
- 固化 smoke 记录模板，减少“发完版再补文档”的遗漏

这里不追求一次做出复杂发布平台，而是把当前已经手工执行的关键检查尽量脚本化。

### 9.3 诊断中心

诊断中心首版建议放在“我的”页二级入口，能力包括：

- 查看当前版本、数据库版本、备份版本
- 查看最近迁移和恢复结果
- 查看最近关键错误摘要
- 导出诊断包

诊断包建议包含：

- 版本与设备信息
- 关键配置快照
- 结构化错误日志
- 最近迁移/备份/语音包/AI 调用结果摘要

导出的目标不是给普通用户自己分析，而是方便后续定位问题时直接提供证据。

## 10. 页面与交互改动

### 10.1 首页

- 今日目标卡升级为“今日 + 本周 + 阶段”复合摘要
- 今日学习建议由静态计数改成动态调度结论
- 当复习积压明显时，给出“先复习再推新词”的解释提示

### 10.2 学习页

- 在关键 checkpoint 显示当前队列类型，如“救火复习中”或“阶段推进中”
- 记录反馈时补采反应时和跳过行为
- 达成日目标、周目标、阶段里程碑时给出轻量完成反馈

### 10.3 我的页

- 现有每日目标卡升级为目标设置入口
- 新增阶段管理入口
- 新增诊断中心入口

### 10.4 统计页

- 新增目标完成率相关区块
- 新增复习风险分层和队列分布
- 新增连续学习与阶段推进指标

## 12. 发版门槛

`v1.7` 被视为可发版，至少满足：

- 动态复习引擎已接管今日队列的核心排序
- 日/周/阶段目标都能在 App 内被看到和推进
- 升级前快照、迁移后校验和恢复入口已打通
- 诊断中心可导出有效诊断包
- CI 已校验版本号、更新日志和 Release 关键资产一致性
- `CHANGELOG.md`、`README.md`、`development-progress.md`、`collaboration-handbook.md` 与发版记录同步更新
- GitHub `Android CI` 与 `Android Release` 全绿

## 13. 风险与取舍

- 若复习优先级公式一次写太复杂，首版会难以调试，因此应先选可解释的分数组合
- 若把所有目标历史都重度结构化，迁移成本会上升，因此首版只记录必要进度和里程碑
- 若诊断日志采集过重，可能影响性能，因此应限定保留窗口和导出内容
- 若升级安全逻辑放得太晚，容易与数据库初始化顺序冲突，因此需要在实施阶段优先落地启动链路

## 14. 结论

`v1.7` 的核心不是再堆一批零散功能，而是把文文Lex 从“能背、能看统计、能发版”推进到“更会安排复习、更有阶段推进感、后续版本更稳更好排障”。

就产品价值而言，`v1.7` 要让用户明显感知三件事：

- 今天该学什么，比以前更合理
- 学习推进更有目标感，而不是只看一个每日数字
- 升级、发版、出错定位更稳，后续迭代成本更低
