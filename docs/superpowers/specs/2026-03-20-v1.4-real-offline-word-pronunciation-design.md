# 文文Lex v1.4 真实离线单词发音设计文档

## 1. 背景

文文Lex `v1.3` 已经完成了发音体系的基础闭环：

- 单词详情页与学习页可按英式 / 美式播放
- 发音设置页已支持来源策略、缓存管理和语音包管理
- 词典音频、在线抓取、本地缓存、系统 TTS 兜底链路已经接好
- 原生离线单词发音的目录、安装器、调度入口和 Release 资产链路已经预留

但 `v1.3` 里的原生离线发音仍停留在 scaffold 阶段，核心缺口仍然存在：

- `SherpaOnnxRuntime` 还没有真正接上模型执行
- 当前 native 语音包只是发布链路占位，不是真实高音质发音模型
- 离线包安装成功后，还不能为任意单词稳定产出真实本地音频

因此，`v1.4` 的目标不是重做发音架构，而是把现有链路里的“真实离线单词发音”正式打通，并把它变成一个可以交付、可发版、可持续升级的产品能力。

## 2. 版本目标

### 2.1 目标

- 接入真实可运行的 Android 本地神经发音 runtime
- 提供英式 / 美式两个独立下载的高音质离线单词语音包
- 让 App 内任意合法词条都可在本地实时合成单词发音，包括导入词书中的单词
- 将首次合成结果落入本地缓存并登记到数据库，后续直接复用
- 保持现有播放回退链：离线包失败后回退在线词典，再回退系统 TTS
- 采集结构化播放与失败数据，为后续 AI 调整计划与质量分析提供稳定输入
- 让 GitHub Release 正式承担 `v1.4` APK 与 UK / US 语音包的发版入口

### 2.2 非目标

- `v1.4` 不扩展到长文本离线朗读或 AI 大段讲解高音质本地生成
- 不引入云端账号、服务端状态同步或自建 TTS 服务
- 不在首版开放多 speaker 选择、情绪风格选择或跟读评分
- 不追求一次性解决所有多音词和上下文相关读音问题
- 不把高音质模型直接打进主 APK

## 3. 已确认的产品约束

用户已确认以下约束，这些约束直接决定 `v1.4` 的设计边界：

- 主线方案：真实离线发音闭环优先
- 质量取向：优先音质和口音自然度，接受更大的模型体积和更长实现周期
- 覆盖范围：先做“单词级”真实发音
- 安装方式：高音质语音包独立下载，主包保持较小
- 口音范围：英式和美式一起上
- 技术路线：双高音质独立包直上，不先做低质过渡方案

这些约束意味着 `v1.4` 必须优先完成“真发音可交付”，而不是继续做轻量桥接或半占位实现。

## 4. 方案结论

`v1.4` 采用以下主路线：

- Android 本地 runtime：`sherpa-onnx`
- 首选模型轨道：`Kokoro English`
- 发布形态：英式包和美式包分别独立下载、校验、安装、切换
- 运行方式：主包内调度，本地模型实时合成单词音频，首次合成后落缓存
- 播放优先级：`本地缓存 > 本地原生离线发音 > 在线词典音频 > 系统 TTS`

不采用以下路线：

- 不采用“伴生 TTS App”模式，因为体验割裂、设置复杂
- 不采用“仅高频词预制音频包”模式，因为无法覆盖导入词书
- 不采用“先联网生成再离线播放”作为主方案，因为不满足真实离线目标
- 不采用“先上单一口音再补另一口音”，因为用户已明确要英美双口音一起上

## 5. 总体架构

### 5.1 组件职责

- `PronunciationOrchestrator`
  - 统一处理单词播放请求
  - 负责命中缓存、选择离线包、触发回退链和记录 telemetry

- `NativeOfflineWordTtsEngine`
  - 面向单词级输入做真实本地合成
  - 负责把标准化后的单词交给 native runtime，并将结果写入缓存仓库

- `SherpaOnnxRuntime`
  - 封装真正的模型加载、资源检查和推理调用
  - 对上层暴露稳定的 `synthesizeWord` 接口

- `VoicePackRepository`
  - 管理英式 / 美式语音包的清单、下载、校验、安装和激活状态

- `WordAudioRepository`
  - 管理生成后音频文件与数据库元数据
  - 负责缓存复用、落盘、清理和来源标记

- `PronunciationTelemetryRecorder`
  - 记录来源、耗时、失败阶段、缓存命中和回退情况
  - 为后续 AI 分析提供结构化数据

### 5.2 设计原则

- 保持现有模块边界，不重构整套发音系统
- 上层页面不感知具体模型和 runtime 细节
- 口音严格隔离，不允许英式请求偷偷落到美式包
- 缓存键必须包含模型与版本信息，避免升级后播旧文件
- 所有失败都要带阶段信息，不能只暴露“播放失败”

## 6. 语音包设计

### 6.1 分包策略

首版提供两个正式包：

- `en-gb-offline-word-v1`
- `en-us-offline-word-v1`

每个包独立下载、独立安装、独立激活。首版允许两包重复携带部分基础资源，以换取实现简单和运行时稳定。

### 6.2 包内文件

每个包至少包含：

- `manifest.json`
- `model.onnx`
- `voices.bin`
- `tokens.txt`
- `espeak-ng-data/`
- `licenses/`

如果模型运行所需文件名与目录略有差异，允许在不改变 schema 的前提下微调，但 manifest 中必须完整声明入口文件。

### 6.3 manifest 必填项

- `id`
- `name`
- `accent`
- `locale`
- `engineType`
- `modelFamily`
- `modelVersion`
- `packageFormatVersion`
- `entryFiles`
- `payloadChecksums`
- `estimatedStorageBytes`
- `estimatedRamMb`
- `speakerProfile`
- `licenses`

校验真值来源明确如下：

- Release 附件中的 `voice-pack-checksums.txt` 是压缩包归档文件的唯一真值来源，用于下载完成后的解压前校验
- 包内 `manifest.json` 中的 `payloadChecksums` 是解压后安装目录文件完整性的真值来源，用于安装阶段校验
- App 只有在“归档校验通过 + 安装后文件校验通过”两个条件都满足时，才将包状态置为 `ready`

## 7. 下载、安装与切换流程

### 7.1 下载安装

1. 用户在设置页选择英式包或美式包下载
2. `WorkManager` 负责后台下载、断点恢复和状态更新
3. 下载完成后，先对照 Release 的 `voice-pack-checksums.txt` 校验归档 `sha256`
4. 归档校验通过后解压到应用私有目录
5. 对照包内 `manifest.json.payloadChecksums` 校验安装后的关键文件
6. 注册安装结果并刷新包状态
7. 用户可手动激活目标包

### 7.2 切换规则

- 英式请求优先找英式激活包
- 美式请求优先找美式激活包
- 激活状态按口音分别维护，即“英式一个 active pack + 美式一个 active pack”，不是全局只能激活一个
- `AUTO` 仅在当前已有可用口音时才取默认偏好，不跨口音借用
- 若目标口音未安装或损坏，直接进入回退链，不做静默改口音

### 7.3 升级规则

- 语音包升级视为新版本安装
- 缓存键需带 `accent + modelFamily + packVersion`
- 升级后旧缓存允许延迟清理，但新播放只命中新版本缓存

## 8. 合成与缓存流程

### 8.1 单词标准化

在进入 native 合成前，先对词条做稳定化处理：

- 去掉无意义空白
- 统一大小写策略
- 对连字符、撇号等做受控清洗
- 保留对合法词形变化的支持，不提前把所有变形强行还原为 lemma

首版只处理影响单词级合成稳定性的清洗，不在这一层实现复杂多音词判定。

### 8.2 合成流程

1. 页面请求播放单词
2. `PronunciationOrchestrator` 查询本地缓存
3. 若未命中，检查目标口音 native 包是否已安装可用
4. 进入 `NativeOfflineWordTtsEngine`
5. 调用 `SherpaOnnxRuntime.synthesizeWord`
6. 将生成的 wav 文件写入缓存目录
7. 在 `word_audio_assets` 中登记来源与路径
8. 返回播放器立即播放

### 8.3 缓存策略

缓存键建议至少包含：

- `wordId`
- `normalizedWord`
- `accent`
- `modelFamily`
- `packVersion`

缓存策略要求：

- 同一版本重复播放直接命中缓存
- 包升级后不复用旧版本缓存
- 清缓存时只清生成音频，不影响语音包安装目录

## 9. 回退与错误处理

当 native 离线发音不可用时，按以下顺序回退：

1. 在线词典音频
2. 系统 `TextToSpeech`

触发回退的典型情况包括：

- 目标口音包未安装
- 包已安装但 manifest 缺失或损坏
- runtime 初始化失败
- 模型推理失败
- 生成文件为空或不可播放

错误处理要求：

- 设置页要能区分下载失败、校验失败、安装失败、运行失败
- 运行失败应记录 stage，例如 `runtime_load`、`synthesis`、`cache_write`
- 同一错误在短时间内需要冷却，避免用户连续点击时反复重试卡死 UI

## 10. 数据采集与 AI 分析接口

`v1.4` 必须从第一版开始记录足够细的结构化数据，供后续 AI 做连续性分析和学习计划调整，但默认不上传原始音频。

最低必录字段：

- `wordId`
- `lemma`
- `normalizedWord`
- `accent`
- `resolvedSource`
- `voicePackId`
- `voicePackVersion`
- `cacheHit`
- `latencyMs`
- `failureStage`
- `fallbackUsed`
- `timestamp`

可选增强字段：

- `requestedSource`
- `sessionId`
- `bookId`
- `surfaceForm`
- `retryCount`
- `deviceClass`

这些数据的作用：

- 给 AI 判断用户在哪些词上更依赖发音帮助
- 分析哪类词更容易触发失败或回退
- 区分“不会读”“想确认口音”“反复纠正发音”的不同学习行为
- 为后续动态计划调整提供长期、可摘要的行为依据

## 11. 验收标准

### 11.1 功能验收

- 英式包和美式包都可独立下载、安装、激活和删除
- 目标口音包可对普通单词稳定生成本地音频
- 导入词书单词也可走同一条离线合成链路
- 生成后的音频会落缓存并被后续播放复用
- native 失败时能稳定回退到在线词典，再回退系统 TTS

### 11.2 体验验收

- 在基准 `arm64` 真机上，缓存命中后的播放启动时间应稳定在 `300ms` 内
- 在同一基准真机上，首个单词冷启动合成的中位耗时目标为 `3s` 内，单次最大验收值不超过 `6s`
- 英式 / 美式口音不串音
- 每个口音至少抽取 `20` 个覆盖常见词形的验收词做人工听测，要求无明显爆音、断音、截断或错误口音
- 首版必须同时回收首次合成耗时埋点和人工听测结果，作为正式发版前的双重验收依据

### 11.3 发布验收

- GitHub Actions 中的语音包校验脚本全部通过
- Release 页面同时包含 APK、英式包、美式包、manifest 和 `voice-pack-checksums.txt`
- 至少完成一轮真机 `arm64` smoke test

## 12. 主要风险与边界

- 高音质模型体积较大，会抬高下载与存储成本
- Android 真机的内存与稳定性压力高于现有桥接包
- 单词级发音无法完全解决上下文相关的多音词问题
- native runtime 的 ABI 兼容和打包集成可能带来额外工程复杂度

为控制风险，`v1.4` 采用以下边界：

- 首版只承诺单词级真实发音
- 首版 speaker 固定，不开放选择 UI
- 若某些机型 native runtime 不稳定，仍保留完整回退链保证可用性

## 13. 实施切片建议

为避免一次性改动过大，`v1.4` 的实现建议分四个切片推进：

1. 真机可跑通的 `SherpaOnnxRuntime` spike
2. 语音包 schema、安装器和 manifest 升级
3. 调度器、缓存、telemetry 与设置页接线
4. 真机验收、Release 资产、更新日志与正式发版

这个切片顺序保证最先验证技术风险，再把现有产品链路接完整。
